# Эксперимент DB / YOLO26-L / YOLO26-X

Это отдельная экспериментальная ветка. Стандартный детектор сервиса — DB. YOLO
меняет локализацию текста и сборку областей; Xiaomi, выбранная Qwen, лимиты
перечитываний, буквальное извлечение, валидаторы и политика допуска сохраняются.
Результаты сравнения сами по себе не разрешают производственное автозаполнение.

## Что именно сравниваем

* `optics`: каждый детектор → один и тот же кириллический CTC. Xiaomi и Qwen в
  этой стадии не запускаются. Метрика — точное наличие заранее заданных
  фрагментов в отдельных CTC-наблюдениях. Это диагностическая полнота чтения,
  без определения роли поля и без притязания на CER всей страницы.
* `e2e`: каждый детектор выполняет свой полный конвейер с Xiaomi, одной и той
  же Qwen, ограниченными перечитываниями и действующими строгими проверками.
  Сравниваются точные `raw_value` выбранных скалярных полей. Никакие ответы
  предыдущего детектора не передаются следующему как optical replay.

Золото находится в отдельном `references.json`. Оно читается только отчётом
после инференса и не попадает в `Engine.run` или промпты. До первого вычисления
сохраняются `protocol.json`, SHA кода, моделей, источников и эталонов, настройки,
порядок вариантов и общий бюджет. Изменение кода или исходного документа во
время прогона останавливает сравнение. Самостоятельного продолжения или
перезапуска прерванного исследования нет; новый запуск требует нового output.

## Наборы и границы выводов

Локальная подготовка, без инференса:

```bash
python -m experiments.yolo26.prepare_pilot --workspace ../ --output benchmark-data/yolo26-pilot-v2
python -m experiments.yolo26.prepare_receipts --workspace ../ --output benchmark-data/yolo26-receipts-v1
```

`--workspace` — родитель каталогов `xiaomi-ocr-lab` и `mosru-ocr-fixtures`.
Эти подготовленные наборы не входят в Git. Команды используют уже существующие
локальные исходники; ничего не скачивают.

Основной пилот содержит 6 документов / 6 исходных групп / 30 скалярных эталонов:

* 2 физических скана общедоступных макетов паспортов MIDV-2020; значения личности
  вымышлены. Это настоящая физическая съёмка макетов, а не документы граждан.
* 2 синтетические квитанции на основе открытых шаблонов mos.ru.
* Первые страницы 2 синтетических договоров. Контракт запуска явно ограничен
  полями первой страницы; полное покрытие двухстраничного договора не заявлено.

Все примеры и шаблоны уже использовались в предыдущей работе проекта. Старый
признак `test` сохраняется как история происхождения, но не превращает их в
новый независимый holdout для этого эксперимента. Физические сканы и синтетика
отчитываются раздельно. Для подтверждения обобщения понадобится новый набор.

Отдельно подготовлены 3 реальные квитанции/кассовые чеки из ранее проверенного
открытого набора и 12 точных фрагментов. Для них разрешена только стадия
`optics`: среди десяти текущих профилей нет профиля кассового чека. Подстановка
чека в профиль банковского платёжного поручения не используется.

Подготовка копирует исходные байты в `documents/` с повторной проверкой SHA.
Пути в inference-манифесте относительные. Каталог набора можно перенести в Linux
без редактирования манифестов и эталонов. Источники, атрибуция и известное
использование сохранены. Наборы и результаты с содержимым документов не пушить.

## Запуск

Нужны зависимости основного инференса и дополнительная группа `.[yolo]`.
PyTorch ставится согласно целевой платформе; автоматическая установка и
скачивание моделей во время инференса запрещены. Подготовить и проверить нужно
`detector`, `cyrillic`, `yolo26l-text`, `yolo26x-text`, а для E2E также `xiaomi`
и выбранную Qwen. Проверяются зафиксированные в model lock файлы и SHA.

```bash
python -m experiments.yolo26.run --data benchmark-data/yolo26-pilot-v2 --output outputs/yolo26-optics --models models --stage optics --device cpu --total-seconds 1800
python -m experiments.yolo26.run --data benchmark-data/yolo26-receipts-v1 --output outputs/yolo26-receipts-optics --models models --stage optics --device cpu --total-seconds 1800
python -m experiments.yolo26.run --data benchmark-data/yolo26-pilot-v2 --output outputs/yolo26-e2e --models models --stage e2e --device cpu --qwen qwen-0.8b --total-seconds 7200
```

CPU остаётся явным FP32; CUDA — явным BF16 для существующих VLM. Прежние лимиты
по умолчанию: 1024 выходных токена, 120 секунд на вызов, 600 секунд на документ.
Их не сокращают ради более красивого времени. `--total-seconds` задаёт отдельный
общий предел. `--arms`, `--ids` и `--repeats 1|2|3` фиксируются до вычислений;
использовать их для выбора только удачных результатов после просмотра нельзя.

### Поправка протокола E2E v1 → v2

Перед повтором зафиксирована `selector-routing-projection-v3`: полный текст
исходных строк сохраняется, из списка выбора убраны кандидаты без подтверждённой
роли, которые исходный resolver всё равно запрещает принимать. Точные кандидаты,
конфликты и доказательства остаются на сервере. Только геометрия сообщения
selector округлена до ближайшего пикселя (до 0,5 px на координату), с явной
пометкой routing-only; проверки используют исходные координаты. Повторяющиеся
метаданные представлены ссылками. Это новая общая проекция контекста, а не
доказательство одинаковых ответов модели при двух представлениях.

Tokenizer-only preflight 20 контекстов без загрузки весов и чтения эталонов:
максимум исходного сообщения 101930 токенов, нового — 25816. Два сохранённых
сообщения с Xiaomi: 7406 → 4379 и 8747 → 5100. Для v2 до первого вычисления
выбран входной предел 32768 для всех детекторов; добавления последующих
перечитываний по-прежнему проверяются runtime, без молчаливого обрезания.

Первоначальный `outputs/yolo26-e2e-pilot-v1` остановлен после трёх сохранённых
попыток. Выявлены ограничения исполнения: таймаут selector 120 секунд и
сообщение около 8700 токенов при входном лимите 8192. Эти попытки сохраняются
как диагностика обвязки, а не объявляются провалом качества модели. Их нельзя
смешивать с новым сравнением или незаметно продолжать после изменения кода.

Для v2 одинаково для DB/L/X применяется сокращённое представление сообщения
selector и ранняя проверка входного контекста. Веса, кандидаты, исходные
документы, эталоны, валидаторы и критерии точности не меняются. Все варианты
запускаются заново; версия кода и новые лимиты фиксируются в новом протоколе.

```bash
python -m experiments.yolo26.run --data benchmark-data/yolo26-pilot-v2 --output outputs/yolo26-e2e-pilot-v2 --models models --stage e2e --device cpu --qwen qwen-0.8b --max-input-tokens 32768 --attention-backend sdpa --call-timeout 600 --document-timeout 1800 --total-seconds 7200
```

`--max-input-tokens` по умолчанию остаётся 8192; для v2 после предварительной
проверки явно фиксируются 32768 и `--attention-backend sdpa` для всех вариантов.
На длинном FP32-контексте eager attention материализует большие квадратичные
матрицы; один подъём контекстного лимита мог бы исчерпать RAM. SDPA — отдельная
зафиксированная настройка исполнения, её не переключают по ходу сравнения или
только для одного детектора. Без аргумента `--attention-backend` сохраняется
значение Settings/окружения. Лимит выхода остаётся 1024 токена.
Увеличенные 600/1800 секунд относятся к отдельному CPU-эксперименту v2, а не
подменяют стандартные эксплуатационные лимиты движка.

Владелец моделей один. Не запускать этот benchmark одновременно с API, другим
benchmark или другим владельцем моделей на той же вычислительной аренде.

Для Linux / RTX коллеги собрать вариант контейнера с YOLO:

```bash
docker build --build-arg HARNESS_INSTALL_YOLO=1 -t harness-ocr:yolo26 .
```

После переноса наборов в `benchmark-data/`, подготовки моделей и предоставления
UID 10001 права записи в `reports/` пример отдельного offline-прогона:

```bash
docker run --rm --gpus all --network none --pid=host \
  --mount type=bind,source="$PWD/models",target=/models,readonly \
  --mount type=bind,source="$PWD/benchmark-data",target=/data,readonly \
  --mount type=bind,source="$PWD/reports",target=/reports \
  -e HARNESS_VISUAL_VERIFIER=1 harness-ocr:yolo26 \
  python -m experiments.yolo26.run --data /data/yolo26-pilot-v2 \
  --output /reports/yolo26-gpu-e2e --models /models --stage e2e --device cuda \
  --qwen qwen-0.8b --total-seconds 7200
```

Визуальный verifier в этом примере включён одинаково для всех вариантов.
Настройка фиксируется в протоколе. Сравнение с CPU-прогоном с иным verifier
не является чистым измерением влияния устройства. После основного сравнения
Qwen 4B можно проверить отдельным заранее зафиксированным прогоном.

`--pid=host` здесь относится только к отдельному измерительному контейнеру:
NVML возвращает PID хоста, и совпадение пространств PID позволяет привязать
GPU-память к владельцу моделей. Изоляция штатного Compose-сервиса не меняется.
Без совпадения PID или при недоступном NVML измерение может остаться null.
В исходных результатах также сохраняются доступные PyTorch-пики отдельных
вызовов; это allocated/reserved runtime, а не полный расход VRAM драйвера.

## Что присылать и как читать результат

Сохранить весь каталог запуска: `protocol.json`, `status.json`, `loads.json`,
`measurements.json`, `summary.json`, `report.html`, `rows/` и `state/` с трассами.
Пути исходных файлов и текст документов в них могут присутствовать; передавать
по согласованному каналу команды, не прикладывать к публичному issue.

* Отчёт показывает все запланированные строки, включая `missing`, `failed` и
  `incomplete`. Ненаблюдавшийся результат не считается неверным распознаванием.
* Основные показатели завершённых запусков и частичные распознавания показаны
  раздельно. Дельты считают только полностью завершённые пары одного документа.
* Правильно прочитанное, прошедшее валидацию и разрешённое к автозаполнению —
  разные показатели. Ложные допуски считаются только на оценённых полях; нулевое
  количество допусков не доказывает нулевой производственный риск.
* Время загрузки E2E измеряется отдельно. Первый документ блока может включать
  ленивую инициализацию. Фиксированный порядок DB → L → X не устраняет влияние
  температуры/порядка; для устойчивой скорости нужен отдельный повторный тест.
* RSS — максимум выборки каждые 50 мс для управляющего процесса и владельца
  моделей. Общие страницы могут учитываться дважды; это не гарантированный
  непрерывный OS high-water mark. NVML учитывает только совпавшие PID, а не
  общий расход чужих процессов на видеокарте. Недоступный GPU-замер остаётся null.
* CPU-время не пересчитывается в воображаемые GPU TPS. Пилот не измеряет RPS
  сервиса, параллельную нагрузку, энергопотребление или продовую ёмкость.

Повторный отчёт без новых вычислений:

```bash
python -m experiments.yolo26.report --output outputs/yolo26-e2e --references benchmark-data/yolo26-pilot-v2/references.json
```

Лицензии Ultralytics и отдельные лицензии весов зафиксированы в
`THIRD_PARTY_NOTICES.txt`; наличие экспериментального адаптера не меняет их.
