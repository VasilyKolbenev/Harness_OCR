# Запуск Харнесс OCR на документах коллеги

Цель поставки: на Linux с NVIDIA GPU принять собственные документы из [каталога десяти профилей](supported-documents.md), выполнить единый конвейер и сохранить значения полей с доказательствами. Для этого не нужны интеграции с mos.ru, MCP-клиент или внешние реестры.

Программные тесты и сборка CUDA-контейнера проверяются в CI. Фактический инференс, потребление VRAM и качество на документах коллеги подтверждаются на его машине. Это проверка работающего продукта в заданном объёме; её результат не заменяет измерения точности.

## 1. Один раз подготовить сервис

Из корня репозитория выполните разделы «Сборка и загрузка весов» и «Запуск и диагностика» в [README для Linux/GPU](../README_LINUX_GPU.txt): сборка Docker, явная загрузка закреплённых весов, `docker compose up -d` и `scripts/doctor.py`.

Для целевого запуска нужны Linux + Docker Compose с NVIDIA Container Toolkit, доступ к RTX PRO 5000 Blackwell 48 GB, модели и два разных токена. Токены генерируются и остаются в среде коллеги. При выполнении команд ниже Compose передаёт `HARNESS_API_TOKEN` клиенту; токен не записывается в manifest.

Используйте стандартный Compose-сервис: он включает visual verifier, один последовательный процесс моделей и read-only модели. Не запускайте параллельно отдельный CLI inference или offline benchmark на том же GPU. Отсутствие политики автоматического принятия не мешает проверке документов: безопасный результат по умолчанию — `review`.

## 2. Положить файлы и указать их тип

Создайте в корне проекта папку `test-documents`, скопируйте туда свои разрешённые для тестирования файлы и шаблон manifest:

```bash
mkdir -p test-documents
cp docs/own-documents.example.json test-documents/manifest.json
```

Замените `sample.pdf` на реальное имя и выберите профиль. Минимальный `test-documents/manifest.json`:

```json
{
  "schema_version": "harness-own-documents/1",
  "documents": [
    {"id": "sample-01", "path": "sample.pdf", "profile_id": "D01"}
  ]
}
```

`path` отсчитывается от папки manifest: файл должен находиться в этой папке или её подпапке; абсолютные пути и выход за её пределы отклоняются. В одном manifest допускается от 1 до 100 документов. Дайте каждому уникальный `id` длиной до 64 символов: первая буква или цифра, затем латинские буквы, цифры, дефис и подчёркивание. Регистр не делает два ID разными. `profile_id` можно записать коротко (`D01`) либо полностью (`rf_passport_main_v1`). Тип указывается явно: автоматического классификатора или разделителя разных документов в одном файле нет.

Для нескольких документов добавьте элементы в `documents`. Для проверки отдельных полей у элемента можно задать непустой `subset`, например:

```json
{
  "id": "passport-number-01",
  "path": "sample.pdf",
  "profile_id": "D01",
  "subset": ["passport.series", "passport.number"]
}
```

Это отдельный узкий контракт; он не подтверждает извлечение остальных полей паспорта. Все 96 точных ключей и входные лимиты перечислены в [каталоге](supported-documents.md). Эталоны `gold` для обычного запуска не требуются.

## 3. Выполнить одну команду

При уже запущенном `docker compose up -d`:

```bash
docker compose run --rm --no-deps \
  -v "$PWD/test-documents:/input:ro" --entrypoint python ocr \
  scripts/run_documents.py --manifest /input/manifest.json \
  --output /reports/own-documents-001 --base-url http://ocr:8080
```

Runner последовательно загружает каждый файл, сверяет SHA, отправляет задание, ждёт завершения и сохраняет результат с трассой. Он обращается к тому же полному конвейеру сервиса; отдельную модель не запускает. Файлы не покидают локальный Docker-сервис. Каталог результата создаётся заново: для повторного запуска выберите новое имя, например `own-documents-002`.

По умолчанию бюджет ожидания всего набора — 3600 секунд, одного документа — 600 секунд. При необходимости задайте `--seconds` и `--document-seconds` явно; они не снимают внутренние ограничения сервиса. Это бюджеты ожидания: отдельный HTTP-запрос может добавить до 30 секунд, а подтверждение отмены — дополнительный ограниченный интервал (по умолчанию 30 секунд). На таймауте runner запрашивает отмену и не начинает следующий документ, пока прекращение предыдущего не подтверждено.

По умолчанию используется Qwen 0.8B. Чтобы проверить Qwen 4B, добавьте `--qwen qwen-4b` и задайте новый `--output`. Это выбор связки для запуска; автоматического вывода о превосходстве модели по одному примеру не делается.

## 4. Забрать результат

```bash
docker compose cp ocr:/reports/own-documents-001 ./own-documents-001
```

В каталоге запуска находятся общая сводка и отдельные артефакты каждого документа:

- `summary.json` — итог исполнения и сводка извлечения по документам.
- `input-manifest.json` — точная копия manifest этого запуска.
- `<id>/status.json` — состояние задания и ошибки, если они возникли.
- `<id>/result.json` — буквальные и структурированные поля, проверки, роли и источники; появляется, когда результат доступен.
- `<id>/trace.json` — трасса обработки; появляется, когда сервис её вернул.

Начните со сводки, затем откройте `result.json` конкретного документа. Поля находятся в `fields`, компактный контракт — в `contract_result`, наблюдения для проверки `evidence_ids` — в `observations`.

## 5. Правильно прочитать итог

Разделяйте три результата:

1. **Исполнение:** загрузка, SHA, завершение задания, привязка к документу/профилю/subset, структура выбранных полей, согласованность компактной проекции, доступность трассы и её document IDs. Технический `pass` относится к этим проверкам. Runner не выполняет полную валидацию JSON Schema, проверку всех доказательств или криптографический аудит трассы; точный охват указан в `checks_scope`.
2. **Извлечение:** сколько полей действительно `observed`, сколько удержано, неоднозначно или не прошло проверку. Полностью пустое извлечение отдельно отмечается как требующее внимания, даже если процесс завершился. Его нельзя выдавать за успешно распознанный документ.
3. **Правильность:** совпали ли значения с независимой ручной разметкой. Без эталона runner её не измеряет и не публикует процент точности.

`review` при прочитанных полях — допустимый результат. `not_observed` не означает доказанное отсутствие поля на изображении. `not_checked` не означает, что формат или контрольная сумма подтверждены. Неизвестная применимость условного поля остаётся unresolved. Ручное подтверждение, банковские интеграции и ослабление проверок для первого технического запуска не требуются.

Если задание завершилось ошибкой или по таймауту, сохраните сводку и журнал `docker compose logs ocr`; частичный результат не считается полным. При превышении ограничений файла смотрите причину отказа, а не ожидайте скрытого усечения документа.

## Отдельно: сравнение качества моделей

После проверки своих файлов можно размечать независимый корпус и запускать `scripts/gpu_acceptance.py` по README. Это другой manifest (`harness-bench/1`) с обязательными эталонами `gold`, четырьмя режимами и проверками парности. Он не является предварительным условием для получения результатов по собственным документам.

Для передачи достаточно исходников, закреплённых весов и этой инструкции. Папки `test-documents/`, `benchmark-data/` и выгрузки `own-documents-*/` исключены через `.gitignore`. Закрытые сканы, токены, runtime-базы и трассы в репозиторий не добавляются.
