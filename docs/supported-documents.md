# Какие документы принимает Харнесс OCR

Это технический каталог исполняемых контрактов: **10 профилей, 96 полей**. Движок принимает файл и явно выбранный профиль, возвращает прочитанные значения, доказательства и причины проверки. Качество на всех макетах этих документов ещё не квалифицировано. Каталог не является обещанием безошибочного распознавания.

Для запуска на собственных примерах достаточно Docker-сервиса и файлов. Внешние интеграции, MCP-потребитель, банковские справочники и подключение mos.ru для этого не нужны. Практический запуск — в [инструкции коллеге](colleague-handoff.md).

## Входной контракт

- Один входной файл — один документ и один явно указанный `profile_id`. Допустимы короткие алиасы `D01`–`D10`. Автоматическая классификация и разбиение пакета разных документов не выполняются.
- Общий путь для всех десяти профилей: JPEG, PNG, TIFF и PDF. Изображения декодируются Pillow; EXIF-ориентация применяется. PDF растеризуется в 200 dpi; его текстовый слой не считается доверенным native-источником.
- Лимиты по умолчанию: **30 MiB на файл, 10 страниц, 12 000 000 пикселей на страницу**. Для PDF лимит площади проверяется до растеризации. Файл сверх лимита отклоняется, а не незаметно обрезается.
- Многостраничный документ передаётся одним PDF или TIFF. Список фотографий как один документ runner не склеивает.
- DOCX, архивы и набор произвольных вложений не входят в этот входной контракт.
- Только для `D04` есть зарегистрированный native XML: единая ненотариальная МЧД 003 / `EMCHD_1`, проверяемая закреплённой XSD. Проверка структуры не подтверждает электронную подпись, актуальность, отзыв или юридические полномочия. Произвольный XML может дать диагностические наблюдения, но не объявляется поддержанным native-документом.

| D05 | `paper_machine_passport_v1` | Бумажный паспорт самоходной машины | 5 | 5 |

| D09 | `education_agreement_v1` | Договор дополнительных образовательных услуг | 6 | 8 |
| D10 | `oms_evidence_v1` | Полис ОМС / выписка о полисе | 2 | 3 |

«Обязательное» означает обязательное поле технического полного контракта, а не юридическое требование услуги. Условное поле включается проверяемой применимостью доверенной серверной конфигурации. Если применимость неизвестна, поле остаётся unresolved и результат требует проверки; отсутствие OCR-строки не превращает его в `not_applicable`.

Без `subset` запрашиваются все поля профиля. Для узкой проверки можно задать непустой `subset` из точных ключей ниже. Это создаёт отдельный контракт: успешная проверка subset не означает полного покрытия документа. Условные поля вне subset не требуются для его полноты.

## Что находится в результате

`result.json` содержит профиль/версию, SHA исходного файла, `revision`, поля, наблюдения и конфликты, `completion_report`, `unresolved_conditions`, `visual_checks`, решение и `reason_codes`. Вложенный `contract_result` — компактная проекция по скомпилированной JSON Schema.

Каждое поле содержит:

- `raw_value` — буквальное значение либо `null`; сложное поле может быть типизированной структурой с несколькими элементами, ролями и доказательствами.
- `canonical_value` — разрешённое представление после явно описанных преобразований; исходное `raw_value` сохраняется.
- `party_role`, `evidence_ids` — роль и ссылки на реальные наблюдения из этого документа.
- `extraction_status`: `observed`, `ambiguous`, `unreadable`, `not_observed` или `not_applicable`.
- `validation_status`: `pass`, `fail` либо `not_checked`, а также доступные `validation_reasons` / `validation_checks`.
- `decision`: `accept_for_autofill`, `review` либо `reject_input`.

Движок не достраивает отсутствующие цифры, не заменяет проваленную проверку догадкой и не считает голос Qwen доказательством. Неизвестный формат заводского номера или недостаточный банковский контекст сохраняют `not_checked`. Узкие проверки PIN/S/N и банковского ключа описаны в [контракте идентификаторов](identifier-validation.md).

`terminal_status=completed` означает завершённый вычислительный путь. `decision=review` и `needs_review=true` ожидаемы без независимой квалификации и включённой политики автоматического принятия. Они не означают падение инференса. При этом завершение с одними пустыми полями не является успешным распознаванием: сводка запуска должна явно показывать число прочитанных и удержанных значений.

## Как проверить контракт без чтения кода

Из корня проекта при запущенном сервисе:

```bash
docker compose exec ocr python -m harness_ocr.cli profiles
docker compose exec ocr python -m harness_ocr.cli profiles --profile D01
```

Первая команда перечисляет профили. Вторая показывает поля, обязательность, условия, версию и скомпилированную схему выбранного контракта. Для более узкого результата используйте `subset` в manifest; точный состав результата определяется его контрактом.

Исходники контракта: [compiler.py](../src/harness_ocr/profiles/compiler.py), [ingest.py](../src/harness_ocr/ingest.py), [settings.py](../src/harness_ocr/settings.py). Полнота контракта, техническая работоспособность и измеренная точность на независимом корпусе — отдельные результаты проверки.
